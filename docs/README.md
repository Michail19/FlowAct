# FlowAct Documentation

Этот каталог содержит проектную документацию FlowAct: описание идеи, архитектуры, пользовательского интерфейса, вариантов запуска и дальнейшего развития системы.

FlowAct проектируется как веб-приложение для визуального создания и запуска рабочих процессов. Пользователь собирает схему из блоков, соединяет их связями, настраивает параметры каждого блока, запускает workflow и анализирует результат через панель выполнения и логи.

## Макет интерфейса

Основной макет FlowAct подготовлен в Figma:

[Открыть макет FlowAct в Figma](https://www.figma.com/site/kHdgkthol0hJg3nQnjgdDv/FlowAct?node-id=0-1&t=D0RCtMPi92VPAbVc-1)

Макет используется как визуальная основа для:

- landing page;
- страницы со списком notebook;
- редактора workflow;
- popup-окон входа/регистрации;
- общей цветовой схемы и визуального стиля интерфейса.

В текущей реализации frontend придерживается общего стиля макета: тёмный фон, cyan-акценты, карточки с мягкими границами, визуальный canvas для блоков и отдельные панели управления.

## Основные проектные решения

### 1. Notebook как контейнер workflow

Notebook используется как пользовательский контейнер для сохранённой схемы. На странице `/home` пользователь видит список notebook, может создать новый notebook, открыть существующий или удалить его.

Внутри notebook хранится workflow:

- блоки;
- связи между блоками;
- положение блоков на canvas;
- frontend metadata;
- статус workflow;
- история запусков.

### 2. Workflow как граф блоков

Workflow представлен в виде графа:

```text
Block -> Connection -> Block
```

Каждый блок имеет тип, позицию, настройки и runtime-статус. Связи определяют порядок выполнения.

Основные типы блоков:

- `start`;
- `end`;
- `ai`;
- `http`;
- `condition`;
- `action`;
- `log`;
- `database`;
- `email`;
- `loop`;
- `merge`.

Часть блоков уже используется в интерфейсе как полноценные элементы редактора, а часть подготовлена как frontend-заготовка под дальнейшую реализацию в WorkerService.

### 3. Frontend-first UX с backend-синхронизацией

Frontend сохраняет рабочее состояние notebook локально, а затем синхронизирует его с backend. Такой подход нужен, чтобы:

- пользователь не терял canvas-состояние;
- редактор мог работать быстрее;
- можно было поддерживать fallback при временной недоступности backend;
- в дальнейшем проще добавить autosave и черновики.

Основное хранилище данных — backend/PostgreSQL, localStorage используется как локальный кэш и fallback.

### 4. ExecutionService как API-слой

ExecutionService отвечает за:

- notebook API;
- workflow API;
- сохранение блоков и связей;
- backend-валидацию workflow;
- активацию workflow;
- создание execution;
- retry/resume/cancel execution;
- публикацию событий в Kafka.

До подключения UserService сервис использует временную dev-auth-заглушку через заголовок `X-User-Id`.

### 5. WorkerService как исполнитель workflow

WorkerService получает события из Kafka и выполняет workflow. Он загружает блоки и связи из PostgreSQL, строит execution graph, проходит по блокам, сохраняет логи и обновляет статус execution.

Текущий сценарий выполнения:

```text
Frontend
  -> ExecutionService
      -> Kafka event
          -> WorkerService
              -> PostgreSQL logs/result
                  -> Frontend polling/status panel
```

### 6. Подготовка под AI-рекомендации

В редакторе заложена подготовка под AI-рекомендации:

- локальные рекомендации следующего блока;
- кнопка автодополнения у несоединённых блоков;
- добавление рекомендованного блока с автоматическим соединением;
- единый тип рекомендации, который позже можно заменить ответом ML/AI-сервиса.

Пока рекомендации строятся локальными правилами. В будущем они могут приходить из отдельного ML Service.

## Текущие ограничения проектирования

На текущем этапе в проекте сознательно оставлены временные решения:

1. **Нет UserService/AuthService.**
   
   Авторизация временно заменена dev-auth-заглушкой. После разработки UserService нужно заменить `X-User-Id` и dev-token на полноценную JWT-авторизацию.

2. **Не все блоки backend-исполняемые.**
   
   Некоторые блоки уже есть в интерфейсе, но в WorkerService пока выполняются упрощённо или требуют дальнейшей реализации.

3. **AI-рекомендации пока локальные.**
   
   Интерфейс и типы подготовлены под AI/ML Service, но полноценный сервис рекомендаций ещё не подключён.

4. **Kubernetes-деплой пока не реализован.**
   
   Основной поддерживаемый сценарий запуска — Docker Compose.

## План дальнейшего проектирования

Ближайшие направления развития:

- разработка UserService/AuthService;
- переход от dev-auth к JWT;
- расширение WorkerService для всех типов блоков;
- подключение ML Service для рекомендаций;
- улучшение landing page и account page;
- подготовка Kubernetes-манифестов;
- добавление CI/CD pipeline;
- формализация API Gateway слоя.
